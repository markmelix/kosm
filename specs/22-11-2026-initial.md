# Kosm PaaS: initial product and architecture specification

- **Status:** initial working specification
- **Date:** 22 November 2026
- **Repository:** `./kosm`
- **Related infrastructure repository:** `./repo`
- **Target cluster:** Socrat homelab
- **Primary implementation language:** Go

This document records the complete initial direction agreed for Kosm. It is the
working source for subsequent design and implementation. Decisions may be revised,
but changes should be made explicitly in this document or in superseding specs.

---

## 1. Motivation

The existing Socrat infrastructure repository is powerful and heavily validated,
but deploying a simple application currently exposes too many platform details to
the application developer. A developer may need to understand or modify some
combination of:

- Argo CD Applications;
- Helm charts and values files;
- Harbor credentials and image pull secrets;
- Kubernetes Deployments, Services and Ingresses;
- cert-manager issuers and TLS Secrets;
- Authentik integration and access groups;
- node affinity and topology constraints;
- storage classes and PVC ownership;
- monitoring resources;
- application-specific tests and infrastructure ownership checks;
- multiple directories in the infrastructure repository.

The existing controls are useful for operating the platform, but they should not
be part of the normal developer experience for an ordinary service.

Kosm should provide a platform abstraction where an application developer can:

1. keep the application declaration in the application repository;
2. describe the service in a small `kosm.toml` file;
3. validate it locally;
4. deploy it with one command;
5. inspect status and logs through one CLI;
6. roll back or remove it through the same CLI;
7. avoid direct edits and pull requests to the infrastructure repository for each
   application or release;
8. avoid learning Kubernetes, Helm, Argo CD, cert-manager, Harbor or the physical
   node topology for normal use.

The intended user experience is closer to Heroku, Fly.io or Render than to a thin
wrapper around `kubectl` or Helm.

## 2. Product definition

**Kosm PaaS** is the application platform.

**`kosm`** is the user-facing command-line client.

The default application declaration is named:

```text
kosm.toml
```

The current naming decision is intentionally simple and can be revisited before a
stable release. Alternatives such as `app.toml` and `socrat.toml` were considered,
but `kosm.toml` best identifies the owning platform without tying applications to
one cluster.

The target workflow is:

```bash
kosm login
kosm validate
kosm deploy
kosm status
kosm logs
kosm open
```

The shortest normal workflow should be:

```bash
kosm deploy
```

A typical application repository should need only:

```text
my-project/
├── Dockerfile
├── kosm.toml
└── source files
```

No per-application Helm chart or Argo CD Application should be required.

Likely future responsibility split:

```text
kosm/

  CRDs
  tests
  installation artifacts
  documentation and specifications
```

## 4. Core architectural decision

The platform and application control planes are separated.

```text
Argo CD deploys and maintains Kosm.
Kosm deploys and maintains ordinary user applications.
```

### Infrastructure plane

The existing GitOps/Argo CD system remains suitable for cluster-level components:

- Kosm itself;
- Traefik;
- cert-manager;
- Authentik;
- Harbor;
- CloudNativePG;
- Prometheus, Thanos, Loki, Tempo, Pyroscope and Grafana;
- storage classes;
- cluster-wide policies;
- node-level platform components.

### Application plane

Kosm owns ordinary user application resources:

- application namespaces or project namespaces;
- Deployments;
- Services;
- Ingresses;
- application configuration references;
- application Secrets;
- release lifecycle;
- rollback metadata;
- later: Argo Rollouts, database claims, application monitoring resources and
  persistent storage claims.

Argo CD and Kosm must never have overlapping ownership of the same application
resources. Double reconciliation would create drift loops and unpredictable
behavior.

---

## 5. The platform must hide Kubernetes, not rename it

Kosm must expose product-level intent rather than Kubernetes implementation
fields.

Good user-facing configuration:

```toml
[resources]
size = "small"

[placement]
class = "general"
```

Undesirable normal user-facing configuration:

```toml
node_selector = { ... }
tolerations = [ ... ]
pod_annotations = { ... }
service_account_annotations = { ... }
helm_values = { ... }
raw_manifests = "..."
```

If the public configuration simply reproduces arbitrary Kubernetes and Helm
options in TOML, Kosm will become another large and leaky configuration system.
The platform should provide opinionated profiles and safe defaults.

Potential resource profiles:

```text
nano
small
medium
large
```

Potential placement classes:

```text
general
compute
gpu
edge
storage
background
```

The mapping from these product-level names to Kubernetes resources and Socrat
nodes is platform configuration, not application configuration.

## 6. High-level architecture

The intended mature architecture contains three logical components:

```text
kosm              user-facing Go CLI
kosm-apiserver    authenticated platform API
kosm-controller   Kubernetes controller/operator
```

For the MVP, `kosm-apiserver` and `kosm-controller` may be combined or the CLI may
use the Kubernetes API through a narrowly scoped internal path. They remain
separate logical responsibilities even if implemented in one binary initially.

### 6.1 `kosm` CLI

Responsibilities:

- locate and parse `kosm.toml`;
- validate application declarations locally;
- authenticate the user;
- build a container image;
- push the image to Harbor;
- obtain the immutable image digest;
- create or update the desired Kosm service state;
- wait for deployment completion;
- display human-readable status and errors;
- stream logs;
- open the service URL;
- request rollback;
- destroy a service.

The CLI must not require a user to possess `cluster-admin` credentials. It should
not directly assemble and apply a large collection of raw Kubernetes objects.

### 6.2 Kosm API

Mature responsibilities:

- authenticate users through Authentik/OIDC;
- authorize project actions;
- accept desired service state;
- provide optimistic concurrency and idempotency;
- provide release history and audit information;
- expose stable status to the CLI;
- enforce quotas and admission rules;
- avoid exposing general Kubernetes credentials to users.

A dedicated API server is desirable, but it is not required for the first
controller proof of concept.

### 6.3 Kosm controller/operator

Responsibilities:

- watch Kosm custom resources;
- convert high-level service intent into Kubernetes objects;
- continuously reconcile desired and actual state;
- update status and conditions;
- create Kubernetes Events for operational diagnostics;
- apply ownership labels and owner references;
- clean up managed resources according to explicit lifecycle rules.

The controller should construct typed Kubernetes objects in Go using
`controller-runtime`, rather than generating a separate Helm chart for every
service.

## 7. Kubernetes terminology

### 7.1 CRD: Custom Resource Definition

A **Custom Resource Definition** adds a new resource type to the Kubernetes API.
Kubernetes already provides types such as `Deployment`, `Service`, `Ingress`,
`Secret` and `ConfigMap`. Kosm can add a type such as `KosmService`.

A useful analogy is:

```text
CRD = type definition or database schema
CR  = value of that type or database row
```

In Go-like terms:

```go
type KosmService struct {
    Spec   KosmServiceSpec
    Status KosmServiceStatus
}
```

### 7.2 CR: Custom Resource

A **Custom Resource** is one concrete object of the type defined by a CRD.

Examples:

```text
KosmService/hello
KosmService/wishlist
```

The CRD defines what fields are valid. Each CR stores the desired state of one
service.

### 7.3 Desired state

Desired state is what the user wants to exist. It is normally stored in the
resource's `spec` field.

For example:

```yaml
spec:
  image:
    repository: harbor.example/anton/hello
    digest: sha256:abc...
  port: 8080
  replicas: 1
```

### 7.4 Runtime or observed state

Runtime state is what actually exists now:

- whether a Deployment exists;
- how many replicas are Ready;
- whether the image can be pulled;
- whether readiness checks pass;
- whether the Ingress and TLS endpoint are available.

Desired and observed state may differ temporarily or because of an error.

### 7.5 `spec`

`spec` is the desired state written by the user-facing system:

```text
spec = what should exist
```

### 7.6 `status`

`status` is the observed state written by the controller:

```text
status = what the controller currently observes
```

Users and the CLI should not manually edit `status`.

Example:

```yaml
status:
  observedGeneration: 4
  readyReplicas: 1
  phase: Ready
  url: https://hello.apps.example.org
```

### 7.7 Generation and observed generation

Kubernetes increments `metadata.generation` when `spec` changes.

The controller records which generation it has processed in
`status.observedGeneration`.

```text
metadata.generation = 4
status.observedGeneration = 3
```

means that the latest desired state has not yet been fully processed.

A successful current reconciliation should eventually produce:

```text
metadata.generation = status.observedGeneration
```

### 7.8 Controller and reconciliation loop

A controller is a long-running program that repeatedly compares desired and
actual state and attempts to make them match.

Conceptually:

```go
for each KosmService {
    desired := service.Spec
    actual := inspectManagedResources()
    reconcile(desired, actual)
    updateStatus()
}
```

Examples:

- if `KosmService` exists but Deployment does not, create the Deployment;
- if the desired digest changes, update the Deployment;
- if a Pod is not Ready, report the reason in status;
- if the service is deleted, clean up managed resources according to policy.

### 7.9 Operator

An operator is a controller for a specific domain. Kosm is a Kubernetes operator
for application services. “Kosm controller” and “Kosm operator” may be used
interchangeably, although “controller” describes the mechanism and “operator” the
product/domain implementation.

## 8. OCI terminology and build artifacts

### 8.1 OCI

**OCI** means **Open Container Initiative**. It defines standard formats for
container images and runtimes.

Modern Docker-compatible images and registries generally use OCI-compatible
formats.

### 8.2 OCI registry

An OCI registry stores container images and other OCI artifacts. Harbor is the
registry already used in Socrat.

Example image identity:

```text
harbor.socrat.alchemmist.xyz/kosm-anton/hello@sha256:abc...
```

Components:

```text
harbor.socrat.alchemmist.xyz  registry
kosm-anton                    registry project/namespace
hello                         image repository
sha256:abc...                 immutable content digest
```

### 8.3 Build artifact

A build artifact is the result of building source code. For the Kosm MVP, the
primary artifact is an OCI container image.

```text
source + Dockerfile → OCI image → Harbor
```

The application repository stores source code and `kosm.toml`. Harbor stores the
built image.

### 8.4 Digests versus tags

Kosm should deploy immutable digests:

```text
repository@sha256:...
```

It should not rely on mutable tags such as `latest` for runtime identity.

A tag may be retained as human-readable metadata, but the deployed release should
be pinned to a digest.

This ensures:

- reproducible rollback;
- unambiguous status;
- no silent image replacement;
- build-once/promote-later support in future environments.

### 8.5 Future OCI metadata

Not part of the MVP, but the registry may later store:

- SBOMs (Software Bills of Materials);
- build provenance;
- image signatures;
- attestations;
- other OCI artifacts.

## 9. Kubernetes Events and operational events

Kubernetes Events are short-lived diagnostic records produced by controllers,
the scheduler, kubelet and operators.

Common examples:

```text
Scheduled
Pulling
Pulled
Created
Started
FailedScheduling
FailedMount
Unhealthy
BackOff
```

Kosm should create useful events such as:

```text
DeploymentCreated
ServiceCreated
IngressCreated
CertificateReady
DeploymentNotReady
RolloutTimedOut
RollbackStarted
RollbackCompleted
```

The CLI should translate raw state and events into human-readable diagnostics.

Example:

```text
hello: Progressing

✓ Image accepted
✓ Deployment created
✓ Pod scheduled
✗ Readiness check failed

Last error:
  GET /healthz returned HTTP 500
```

Kubernetes Events are not a durable audit log. They may expire after a short
period. The conceptual distinction is:

```text
Kubernetes Events  short-lived runtime diagnostics
Kosm releases      durable deployment history
Audit log          who changed what and when
```

For the MVP, status and Kubernetes Events are sufficient. Durable audit storage
can be added later.

## 10. State ownership summary

The initial storage model is:

```text
CRD
  defines the KosmService API schema

KosmService.spec
  stores the current desired application state

KosmService.status
  stores the observed result of reconciliation

OCI registry / Harbor
  stores immutable built container images

Kubernetes Events
  store short-lived operational diagnostics
```

A more accurate statement than “CRD stores desired state” is:

```text
The CRD defines the type.
A CR created from that CRD stores desired state in its spec.
```

## 11. MVP scope

The MVP deliberately excludes staging/production environments and canary
deployments. The first objective is to prove one reliable path:

> A user can describe one ordinary HTTP service in `kosm.toml`, run one command,
> and receive a working HTTPS endpoint.

The MVP flow is:

```text
local source
  → build image
  → push image to Harbor
  → create/update KosmService
  → controller creates Deployment
  → controller creates Service
  → controller creates Ingress
  → cert-manager provides TLS
  → CLI waits for Ready
  → CLI prints URL
```

### 11.1 Included in MVP

- Go CLI named `kosm`;
- Go Kubernetes controller/operator;
- `KosmService` CRD;
- `kosm.toml` parsing and validation;
- Dockerfile-based local build;
- Harbor push;
- immutable image digest deployment;
- standard Kubernetes Deployment;
- ClusterIP Service;
- Traefik Ingress;
- cert-manager TLS;
- readiness probe;
- opinionated resource profiles;
- generated default hostname;
- status and conditions;
- Kubernetes Events;
- application logs through CLI;
- opening the service URL;
- rollback to the previous successful digest;
- service destruction;
- deterministic ownership labels.

### 11.2 Explicitly excluded from MVP

- staging/production separation;
- canary deployment;
- Argo Rollouts integration;
- blue/green deployment;
- automated metric analysis;
- database provisioning;
- persistent volumes;
- autoscaling;
- custom domains;
- Authentik group/application automation;
- application secret management;
- CronJobs;
- worker-only services;
- multiple application containers;
- arbitrary sidecars;
- raw Kubernetes overrides;
- arbitrary Helm values;
- multi-cluster support;
- remote build service;
- billing or chargeback;
- comprehensive long-term audit database.

These exclusions are intentional. Kosm should first make the common stateless HTTP
service path excellent.

## 12. Initial `kosm.toml`

The minimal declaration should be small:

```toml
version = 1

[service]
name = "hello"
port = 8080
```

Optional MVP fields may include:

```toml
version = 1

[service]
name = "hello"
port = 8080
health = "/healthz"

[build]
dockerfile = "Dockerfile"
context = "."

[http]
public = true

[resources]
size = "nano"
```

If no hostname is specified, Kosm should generate one from a stable convention,
for example:

```text
https://hello-anton.apps.socrat.alchemmist.xyz
```

The exact DNS suffix and collision rules remain to be designed.

### 12.1 Configuration principles

- the default path should need very few fields;
- safe defaults should be platform-owned;
- application names should be valid stable DNS labels;
- image references should not be supplied manually for normal local deployment;
- generated URLs should be predictable;
- no secrets should be stored in `kosm.toml`;
- no Kubernetes-specific escape hatch should be included in the MVP;
- schema versioning must be explicit from the beginning.

## 13. `kosm deploy` behavior

### Step 1: discover project

The CLI locates:

```text
kosm.toml
Dockerfile
```

It determines the source root and build context.

### Step 2: validate locally

The CLI validates at least:

- TOML syntax;
- supported schema version;
- service name;
- port range;
- Dockerfile existence;
- build context existence;
- health path format;
- resource profile name;
- unsupported fields;
- required user/project identity when authentication exists.

Local validation must not claim that runtime deployment will succeed.

### Step 3: build image

The CLI invokes a local OCI build implementation, initially Docker BuildKit or
`docker buildx`.

The build should be identifiable by source revision where available.

### Step 4: push to Harbor

The target may follow a convention such as:

```text
harbor.socrat.alchemmist.xyz/kosm-<project>/<service>
```

The CLI obtains the immutable digest after push.

### Step 5: create or update desired state

The CLI sends the repository and digest plus runtime settings to the Kosm API or
Kubernetes-backed platform endpoint.

Example desired state:

```yaml
spec:
  image:
    repository: harbor.socrat.alchemmist.xyz/kosm-anton/hello
    digest: sha256:abc...
  port: 8080
  healthPath: /healthz
  resources:
    profile: nano
  http:
    enabled: true
```

### Step 6: reconcile

The controller creates or updates:

```text
Deployment
Service
Ingress
```

cert-manager may create the Certificate and TLS Secret from the Ingress
annotation/configuration. The exact certificate ownership approach should be
chosen during implementation.

### Step 7: wait

The CLI watches status until one of the following occurs:

- service becomes Ready;
- deployment fails with a terminal or actionable error;
- timeout occurs;
- user cancels waiting, without cancelling the deployment unless explicitly
  requested.

### Step 8: display result

Example successful output:

```text
Building hello...
✓ Image built
✓ Image pushed: sha256:abc...
✓ Deployment ready
✓ HTTPS endpoint ready

https://hello-anton.apps.socrat.alchemmist.xyz
```

## 14. MVP deployment strategy

The MVP uses a standard Kubernetes `Deployment` with rolling updates.

Recommended initial strategy:

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

For a one-replica service this attempts to:

1. start the new Pod;
2. wait for readiness;
3. remove the old Pod.

This is not a canary deployment. Kosm does not control weighted traffic in the
MVP.

The controller API should not be designed so narrowly around `Deployment` that a
future Argo Rollouts backend becomes impossible. Deployment is the first internal
implementation, not the permanent public platform abstraction.

---

## 15. Rollback and release history

The MVP should support:

```bash
kosm rollback
```

Rollback means restoring the previous known successful image digest to the desired
service state and waiting for the standard rolling update to complete.

Potential implementation models:

### Model A: history in `KosmService.status`

Simple but limited. Status is not suitable for unlimited history.

### Model B: immutable `KosmRelease` resources

Example:

```text
KosmRelease/hello-r1
KosmRelease/hello-r2
KosmRelease/hello-r3
```

Example shape:

```yaml
apiVersion: platform.kosm.io/v1alpha1
kind: KosmRelease
metadata:
  name: hello-r3
spec:
  service: hello
  image:
    repository: harbor.socrat.alchemmist.xyz/kosm-anton/hello
    digest: sha256:abc...
  source:
    revision: a71b0e2
status:
  phase: Succeeded
  startedAt: "..."
  completedAt: "..."
```

`KosmRelease` is preferable for a durable design because it supports:

- immutable deployment identity;
- rollback;
- source revision metadata;
- future promotion between environments;
- future Argo Rollouts integration;
- clear release-specific status.

However, the smallest implementation may begin with `KosmService` only. The
release abstraction should still be considered in the API design before fields
are stabilized.

## 16. Initial CLI surface

The first intended commands are:

```bash
kosm init
kosm validate
kosm deploy
kosm status
kosm logs
kosm open
kosm rollback
kosm destroy
```

### `kosm init`

Creates a minimal `kosm.toml`, possibly after asking for service name and port.
It must not deploy anything.

### `kosm validate`

Validates local configuration and files without mutating the cluster.

### `kosm deploy`

Builds, pushes, updates desired state and waits for readiness.

Useful future flags may include:

```text
--no-wait
--timeout
--image <repository@digest>
--project
--debug
```

`--image` is important for future CI where the image is built elsewhere.

### `kosm status`

Shows a human-readable summary of desired and actual state, including whether the
controller has observed the latest generation.

### `kosm logs`

Streams logs from Pods selected by stable Kosm ownership labels. It should not
require the user to know Pod names.

### `kosm open`

Opens the current service URL.

### `kosm rollback`

Selects the previous successful release/digest and deploys it.

### `kosm destroy`

Deletes the service runtime according to explicit lifecycle semantics. Stateful
data is outside the MVP; later versions must never silently destroy retained data.

### `kosm doctor`

Not required for the first cut but strongly desirable. It should convert platform
and Kubernetes diagnostics into actionable messages.

## 17. Status and conditions

A possible initial `KosmService` shape:

```yaml
apiVersion: platform.kosm.io/v1alpha1
kind: KosmService
metadata:
  name: hello
  namespace: kosm-anton
spec:
  image:
    repository: harbor.socrat.alchemmist.xyz/kosm-anton/hello
    digest: sha256:abc...
  runtime:
    port: 8080
    healthPath: /healthz
    profile: nano
  http:
    enabled: true
status:
  observedGeneration: 3
  phase: Ready
  readyReplicas: 1
  activeDigest: sha256:abc...
  url: https://hello-anton.apps.socrat.alchemmist.xyz
  conditions:
    - type: Ready
      status: "True"
      reason: DeploymentAvailable
      message: All replicas are ready
```

Conditions should follow Kubernetes conventions where practical. At minimum the
controller will likely need:

```text
Ready
Progressing
Degraded
```

Possible phases are convenient for display, but conditions and
`observedGeneration` are the more reliable machine-readable interface.

## 18. Resource ownership and labels

All Kosm-managed objects should carry stable labels such as:

```yaml
platform.kosm.io/managed: "true"
platform.kosm.io/project: "anton"
platform.kosm.io/service: "hello"
platform.kosm.io/release: "3"
```

A future rollout implementation may add:

```yaml
platform.kosm.io/track: "stable"
platform.kosm.io/track: "canary"
```

These labels support:

- log selection;
- metrics;
- garbage collection;
- ownership inspection;
- debugging;
- project quotas;
- release status.

Managed child resources should use owner references where Kubernetes lifecycle
semantics are appropriate. Deletion and finalizer behavior must be explicitly
designed and tested.

---

## 19. Namespace and tenancy direction

A likely future namespace model is one namespace per project rather than one per
release:

```text
kosm-anton
kosm-tim
kosm-shared
```

Benefits:

- namespace-level quotas;
- project RBAC;
- project NetworkPolicy;
- scoped Secrets;
- simpler garbage collection;
- fewer namespaces;
- services and releases distinguished by labels.

For an initial single-user prototype, one namespace such as `kosm-test` is enough.
The eventual tenancy model should be decided before multi-user production use.

---

## 20. Authentication and authorization direction

Not required for the first local/controller prototype, but the intended user flow
is:

```bash
kosm login
```

The CLI should use Authentik through OIDC, preferably browser PKCE or a suitable
device authorization flow.

Relevant terms:

- **OIDC:** OpenID Connect, an authentication layer on OAuth 2.0;
- **PKCE:** Proof Key for Code Exchange, protection for public clients such as a
  CLI;
- **MFA:** Multi-Factor Authentication.

Users should receive short-lived application tokens, not static Kubernetes admin
tokens.

Future roles may include:

```text
project owner
project deployer
project viewer
platform administrator
```

Authorization should distinguish at least:

- deploying services;
- viewing status;
- reading logs;
- changing Secrets;
- destroying services;
- deleting persistent data.

---

## 21. Secrets direction

Secrets are excluded from the MVP, but the intended UX is:

```bash
kosm secret set DATABASE_PASSWORD --from-stdin
kosm secret list
kosm secret delete DATABASE_PASSWORD
```

Plaintext secret values must not appear in:

- `kosm.toml`;
- Custom Resource specs;
- CLI arguments;
- logs;
- shell history;
- Git.

A future `kosm.toml` should contain only secret requirements or references, for
example:

```toml
[secrets]
DATABASE_PASSWORD = "required"
API_TOKEN = "required"
```

Possible future backends include Kubernetes Secrets, External Secrets Operator,
SOPS/age or Vault. MVP implementation should not preclude replacing the backend.

---

## 22. Database and storage direction

Database and persistent storage are excluded from the MVP.

Future UX may look like:

```toml
[database]
postgres = true
size = "small"

[storage]
name = "uploads"
size = "10Gi"
class = "shared"
```

Kosm should hide CloudNativePG details from application developers while
preserving explicit lifecycle rules.

Critical future rule:

> Deleting a service must not automatically destroy its database or persistent
> data.

State deletion must be a separate, explicit and strongly confirmed operation.

A retained PVC is not a backup. Database and storage support must define backup,
restore and ownership behavior before it is considered complete.

---

## 23. Future staging and production environments

Staging/production separation is desired, but explicitly deferred until the basic
service lifecycle is reliable.

The preferred future principle is:

```text
Build once, promote the same immutable artifact.
```

The production image must have the same digest that was tested in staging. Kosm
should not rebuild source separately for production.

A possible future configuration:

```toml
version = 1

[service]
name = "hello"
port = 8080

[environments.staging]
resources = "nano"
domain = "hello-staging.socrat.alchemmist.xyz"

[environments.production]
resources = "small"
domain = "hello.socrat.alchemmist.xyz"
replicas = 2
```

Potential future commands:

```bash
kosm deploy --env staging
kosm promote staging production
kosm status --env production
```

The exact schema is not decided. It should not be added until the MVP clarifies
service and release semantics.

Environment separation must eventually account for:

- distinct Secrets;
- distinct databases;
- distinct URLs;
- resource profiles;
- replicas;
- access policy;
- promotion history;
- environment-specific rollback.

---

## 24. Future canary deployments and Argo Rollouts

Canary deployments are desired but excluded from the MVP.

The initial future backend of choice is **Argo Rollouts**, rather than implementing
an entire progressive-delivery state machine inside Kosm.

Argo Rollouts is a Kubernetes controller that provides a `Rollout` resource and
supports:

- canary deployments;
- blue/green deployments;
- weighted traffic shifting;
- pauses;
- manual promotion;
- metric analysis;
- automatic abort and rollback.

The future relationship should be:

```text
KosmService
  → Kosm controller
  → Argo Rollout
  → ReplicaSets and Pods
```

The user should still interact only with Kosm:

```bash
kosm deploy
kosm rollout status
kosm rollout promote
kosm rollout abort
```

Argo Rollouts remains an implementation detail of Kosm PaaS.

The controller may eventually select an internal backend based on platform-level
strategy:

```go
switch strategy {
case Rolling:
    reconcileDeployment()
case Canary:
    reconcileArgoRollout()
}
```

The public Kosm API should describe intent without exposing raw Argo Rollouts
configuration.

Possible future canary progression:

```text
10% → 25% → 50% → 100%
```

Possible future checks:

- readiness;
- HTTP error rate;
- latency;
- restart count;
- application-specific Prometheus metrics.

Manual promotion should precede automatic metric-based promotion in the product
roadmap.

---

## 25. Observability direction

The Socrat platform already has Prometheus/Thanos, Loki, Tempo, Pyroscope, Grafana
and OpenTelemetry components. Kosm should provide opinionated integration rather
than require each simple application to understand the full stack.

MVP:

- stdout/stderr logs;
- CLI log streaming;
- health/readiness state;
- platform ownership labels;
- Kubernetes Events.

Later:

- optional metrics path such as `/metrics`;
- automatically managed scrape resources;
- OpenTelemetry tracing defaults;
- service dashboards;
- rollout analysis through Prometheus/Thanos;
- profile integration where appropriate.

The platform must avoid logging secret values or sensitive request bodies by
default.

---

## 26. Security defaults

Even though the goal is a simple developer experience, simplification must come
from safe platform defaults rather than removing isolation.

Likely controller defaults:

- non-privileged containers;
- no host network;
- no host PID or IPC;
- no hostPath;
- no arbitrary capabilities;
- immutable image digest;
- resource requests and memory limit from a profile;
- readiness probe;
- ClusterIP Service;
- TLS for public HTTP;
- project-scoped namespace;
- managed service account;
- restricted pod security context where compatible;
- default network policy in a later phase.

The normal application API should not permit:

- privileged mode;
- `cluster-admin`;
- wildcard hostnames;
- NodePort or LoadBalancer services;
- secret literals;
- arbitrary Helm hooks;
- arbitrary host placement;
- use of the infrastructure WireGuard mesh as application internet egress.

Applications requiring unusual privileges remain custom infrastructure workloads
outside the ordinary Kosm service class.

---

## 27. What Kosm should not become

Kosm should not attempt to support every existing workload immediately.

The first stable service class should remain intentionally narrow:

- one stateless HTTP container;
- one application port;
- one Service;
- one generated hostname;
- one standard health endpoint;
- one resource profile;
- standard rolling update;
- stdout logs.

Applications with the following requirements may remain custom Kubernetes/Argo
applications until explicit platform support exists:

- controllers or CRDs;
- privileged access;
- host networking;
- complex multi-container Pods;
- custom network appliances;
- databases with unusual lifecycle;
- multiple external endpoints;
- complex Jobs and hooks;
- cluster-wide RBAC;
- bespoke storage topology.

There should be no unrestricted `raw_yaml` escape hatch in the normal service API.
Such an escape hatch would quickly reproduce the complexity Kosm is intended to
remove.

## 29. Migration strategy for Socrat

Kosm should initially run beside existing applications rather than rewriting the
whole cluster at once.

### Phase 1: sandbox

Create isolated platform/test areas, for example:

```text
kosm-system
kosm-test
*.apps.socrat.alchemmist.xyz
```

Deploy:

- CRD;
- controller;
- a minimal CLI;
- one test HTTP service.

### Phase 2: prove lifecycle

Test:

- create;
- no-op reconcile;
- source update;
- failed image pull;
- failed readiness;
- successful update;
- rollback;
- service deletion;
- controller restart;
- Pod recreation;
- node restart where practical.

### Phase 3: first real stateless service

Migrate one low-risk simple service. Compare the old resources with Kosm-managed
resources and verify application behavior.

### Phase 4: remove per-application boilerplate

For migrated services, remove obsolete:

- application Helm charts;
- per-application Argo Applications;
- duplicated Deployment/Service/Ingress templates;
- duplicated release logic;
- redundant placement tests.

### Phase 5: identity, Secrets and multi-user projects

Add Authentik login, project ownership and safe application secret handling.

### Phase 6: environments

Add staging and production with immutable release promotion.

### Phase 7: progressive delivery

Install/integrate Argo Rollouts and add manual canary promotion, followed later by
metric-based automation.

### Phase 8: stateful platform capabilities

Only after the stateless path is mature, add database and storage abstractions with
backup and restore contracts.

Kosm is not intended to replace all of these systems. It provides a coherent

## 31. Developer experience goals

The platform is successful when an application developer can perform the common
workflow without infrastructure expertise:

```bash
$ kosm deploy

Building hello...
Pushing image...
Deploying sha256:abc...
Waiting for readiness...

✓ hello is ready
  https://hello-anton.apps.socrat.alchemmist.xyz
```

Failure output should be actionable:

```text
✗ hello did not become ready

Reason:
  GET /healthz returned HTTP 500 for 2 minutes

Current release:
  sha256:def...

Previous successful release:
  sha256:abc...

Suggested actions:
  kosm logs
  kosm rollback
```

Raw Kubernetes data may be available under `--debug`, but should not be the normal
interface.

## 32. Initial success criteria

The first meaningful milestone is complete when all of the following are true:

1. a new Go repository builds the `kosm` CLI and controller;
2. the `KosmService` CRD can be installed in a disposable cluster;
3. `kosm validate` validates a minimal `kosm.toml`;
4. `kosm deploy` can deploy an image or build and deploy it;
5. the controller creates a Deployment, Service and Ingress;
6. status reports the latest observed generation;
7. the CLI waits for and reports readiness;
8. `kosm logs` works without Pod names;
9. updating the application creates a normal rolling update;
10. a failed readiness check is reported clearly;
11. `kosm rollback` restores a previous successful digest;
12. `kosm destroy` removes the stateless service resources;
13. controller restart does not lose desired state;
14. reconciliation is idempotent;
15. the implementation works in Kind before Socrat deployment;
16. no per-application edit is required in the infrastructure repository.

## 33. Open design questions

The following are intentionally unresolved:

1. Should the MVP include a dedicated API server, or initially use a narrowly
   scoped Kubernetes-backed client path?
2. Should `KosmRelease` be implemented immediately or after the first
   `KosmService` proof of concept?
3. What exact DNS suffix and generated hostname convention should be used?
4. How should Harbor authentication work for local builds without persistent broad
   credentials?
5. Should build execution initially shell out to `docker buildx`, use BuildKit
   directly, or allow both?
6. What exact resource profiles should be available?
7. What is the initial namespace model in Socrat: one sandbox namespace or one
   project namespace?
8. Should cert-manager be driven through Ingress annotations or an explicit
   Certificate resource managed by Kosm?
9. How many previous successful releases should be retained?
10. What timeout and failure semantics should `kosm deploy` use?
11. How should cancellation behave while the controller continues reconciling?
12. What is the exact deletion/finalizer behavior?
13. When should Authentik/OIDC become mandatory?
14. Which existing low-risk service should be the first real migration?
15. How should the controller expose diagnostics without copying unbounded raw
   Kubernetes Events into CR status?

These questions should be answered through smaller follow-up specifications and
implementation experiments.

## 34. Decisions recorded

The following decisions are currently accepted:

- the product is called **Kosm PaaS**;
- the CLI is called `kosm`;
- the default declaration is `kosm.toml`;
- Kosm will be written primarily in Go;
- Kosm is an application platform, not a YAML/Helm generator;
- application deployment must not require per-release or per-service pull requests
  to the Socrat infrastructure repository;
- the infrastructure repository installs Kosm, while Kosm manages ordinary
  applications;
- Kubernetes CRDs/CRs are the initial desired-state mechanism;
- Harbor is the initial OCI registry;
- deployed images are pinned by digest;
- the controller directly reconciles typed Kubernetes resources;
- the MVP uses standard Deployments and rolling updates;
- staging/production separation is deferred;
- canary deployments are deferred;
- Argo Rollouts is the preferred initial future implementation for canaries;
- the MVP focuses on one stateless HTTP container;
- raw Kubernetes overrides are not part of the normal platform API;
- stateful workloads, databases and Secrets are deferred until the basic lifecycle
  works reliably;
- application-facing errors should be human-readable and actionable;
- generated per-service infrastructure files are not the desired architecture.

## 35. Short final model

The concise model is:

```text
Application repository
  source code
  Dockerfile
  kosm.toml
        │
        │ kosm deploy
        ▼
Kosm CLI
  validate
  build
  push
        │
        ▼
Harbor
  immutable OCI image digest
        │
        ▼
KosmService.spec
  desired application state
        │
        ▼
Kosm controller
  reconcile typed Kubernetes objects
        │
        ├── Deployment
        ├── Service
        └── Ingress/TLS
        │
        ▼
KosmService.status + Kubernetes Events
  observed state and operational diagnostics
        │
        ▼
Kosm CLI
  Ready URL, logs, errors and rollback
```

The MVP intentionally stops there. Environments, Argo Rollouts canaries,
databases, persistent storage, Authentik automation and advanced observability are
future layers built on top of a proven simple service lifecycle.
